## 25 的连带修复（取消功能带出来的）

加取消时暴露了三个隐患，一并修了：

1. **`zip.write()` 在流销毁后仍可能被调用**，抛 `ERR_STREAM_DESTROYED`，且不在任何 await 链上，
   会变成主进程 `uncaughtException`。现在写入前先判断 `out.destroyed`，当成普通失败抛出。
2. **`zip.abort()` 销毁写流时缓冲区还有块**，流会 emit error 而无监听。现在先挂空监听再 destroy。
3. **`extractEntry` 半途失败不关写流**，Windows 上句柄不释放，上层删半截文件会 EBUSY。
   现在 catch 里先 `ws.destroy()` 再抛。
4. 封面的三处 `catch` 原本吞掉所有异常，会把取消信号一起吞掉（要等下一个素材才生效），
   加 `rethrowIfCancelled` 透传。
