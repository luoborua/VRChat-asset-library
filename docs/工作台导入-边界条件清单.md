## 1. 链路分派（输入是什么 → 走哪条）

| 输入 | 识别点 | 实际链路 |
|---|---|---|
| `.zip` | `inspectPath` → `kind:"zip"` | `importPath(extractOnly)` 就地解压 → `listExtract` 弹窗挑选 → `importSelected` |
| 文件夹（含 zip） | `inspectPath` → `kind:"dir"` + `zips[0]` | **只取第一个 zip** → 同上（后面的 zip 被忽略） |
| 文件夹（含 unitypackage） | `kind:"dir"` + `hasPackages` | `importOne(dir)` → `importPath` → `find_packages` → 逐个走包桥 |
| 文件夹（纯素材） | `kind:"dir"`，无 zip 无包 | `chooseFolder`：顶层 >1 项 → 挑选弹窗；=1 项 → 整目录 `importPath` |
| `.unitypackage` | `kind:"unitypackage"` | `execute_package` 写请求 → Unity 弹窗 → 回执轮询 |
| 其它文件（`.rar/.7z/.fbx/.vrcpack`…） | `kind:"file"` | `importPath` → 直接报「只支持 .unitypackage、.zip 或文件夹」 |
| 手动入口「文件夹素材」 | `plan` | 只走复制链路，**不剥 Assets、不解压、不认包** |
| 手动入口「Unity 素材包」 | `plan` | 包桥链路，多选只取第一个 |

## 2. A 组 · 入口识别与分派

| 编号 | 情形 | 现在的处理 | 判定 | 建议 |
|---|---|---|---|---|
| A1 | 素材文件夹里有 3 个 zip | 前端 `zipPath = zips[0]`，只解压导入第一个，其余静默丢弃 | ❌ | 全部排队（每个 zip 一条），或至少提示「本文件夹有 N 个压缩包，本次只处理第一个」 |
| A2 | 文件夹里既有 zip 又有 `.unitypackage` | zip 优先，包被忽略 | ❌ | 按数量分派：有包先导包，或弹窗让用户选 |
| A3 | 文件夹里只有包 | `hasPackages` → `importPath` → 逐个发请求 | ✅ | — |
| A4 | `.rar` / `.7z` / `.fbx` / `.blend` / `.psd` | `kind:"file"` → `importPath` 抛「只支持 …」 | ⚠️ | 素材库支持 rar/7z，工作台不支持；文案里应给出「先手动解压成文件夹」的指引 |
| A5 | 扩展名大小写 `.ZIP` `.UnityPackage` | `ext_eq` 与 `/i` 正则都不区分 | ✅ | — |
| A6 | 素材文件已被移动/删除 | `inspectPath` 抛错 → 前端 catch 按后缀兜底 → `importPath` 抛「素材路径不存在」 | ✅ | 文案可读，无需改 |
| A7 | 素材只有在线下载、没有本地路径 | `srcOf` 返回空 → 「没有本地路径」 | ✅ | 可加一句「先在详情页下载」 |
| A8 | 素材是符号链接 / junction | `fs::metadata` 跟随；`walk` 跳过链接子项并给警告 | ⚠️ | Windows junction 行为依赖 Rust 版本，建议实测；至少保证不递归成环 |
| A9 | 路径是网络盘且已断开 | `metadata` 失败 → 报「素材路径不存在」 | ⚠️ | 区分「不存在」与「网络盘不可达」，后者不要提示重新下载 |
| A10 | zip 藏在素材文件夹第 3 层 | `find_zips` 只到 depth 2 → 识别不到 → 当普通文件夹整树复制（zip 文件被塞进 Assets） | ❌ | 找不到 zip 时应提示「发现了 N 个深层压缩包，是否解压」，或统一 depth 到 3 |
| A11 | 拖入 `.vrcpack` | `kind:"file"` → 报不支持 | ⚠️ | 待定：`.vrcpack` 是给别人用的包，是否允许导 Unity 需要产品决定 |

## 3. B 组 · 手动入口「文件夹素材（复制）」（plan → execute）

| 编号 | 情形 | 现在的处理 | 判定 | 建议 |
|---|---|---|---|---|
| B1 | 素材结构是 `<名>/Assets/…` | 原样复制 → `VRCAL_Imports/X-<id>/Assets/…` | ❌ | 与 `importPath` 的剥 Assets 逻辑统一（`src_dir.join("Assets")`） |
| B2 | 目标目录已存在同名文件 | 跳过，计入 `skipped` + warning | ✅ | — |
| B3 | 全部文件同名 | 报「已存在同名文件，没有复制任何内容」 | ⚠️ | 这其实是「无需导入」，不该按失败弹红 |
| B4 | 源 `.meta` 的 GUID 与工程冲突 | 预检即禁止，无「强行导入」 | ✅ | 但见 B5 |
| B5 | 用户要**更新**一份已导入的素材 | 旧副本的 `.meta` 与源 GUID 相同 → 必然冲突 → 永远导不进去 | ❌ | 需要「覆盖更新」语义：识别冲突对象位于 `VRCAL_Imports/` 时允许替换 |
| B6 | 源目录为空 | plan 报「这个目录里没有可导入的文件」 | ✅ | — |
| B7 | 素材在工程内，或工程在素材内 | `overlap` 拒绝 | ✅ | 若素材库根建在工程里，会导致全部素材都不能导入，需给专门文案 |
| B8 | 深度 > 6 / 文件 > 20000 | 前者警告并截断，后者直接报错 | ✅ | 截断应升级为「必须确认」而不是 warning |
| B9 | 目标路径超过 260 字符 | 单文件复制失败 → warning，其余照常 | ⚠️ | 加 `\\?\` 长路径前缀 |
| B10 | 复制中途磁盘满 | 逐文件失败 → `copied>0` 时仍报「已导入 N 个文件」+ warning | ⚠️ | 有失败时应把 job 标 `partial`，别用「完成」 |
| B11 | 只读源文件 / 被占用文件 | `fs::copy` 成功或不报错地失败，视情况进 warning | ⚠️ | 被占用时给出「请关闭正在使用该文件的程序」 |

## 4. C 组 · ZIP 解压

| 编号 | 情形 | 现在的处理 | 判定 | 建议 |
|---|---|---|---|---|
| C1 | 不是 zip / 已损坏 | `ZipArchive::new` 失败 → 「这不是有效的 zip 压缩包」 | ✅ | — |
| C2 | 加密 zip（密码保护） | 条目能列出，`io::copy` 失败被 `let _ =` 丢弃 → 生成 0 字节文件，无报错 | ❌ | 检查 `io::copy` 返回值，失败即中止并保留已解压清单 |
| C3 | 条目名含 `? : * < > \|` 或超长 | `File::create` 失败 → `continue`，静默丢文件 | ❌ | 收集失败条目，结束时汇总报「N 个文件无法写入」 |
| C4 | 中文 GBK 文件名（Windows 打的包，无 UTF-8 标志） | zip crate 按 UTF-8/CP437 解码 → 乱码文件名 | ❌ | 检测非法序列后用 GBK 回退解码 |
| C5 | 条目含 `../` 或绝对路径 | `enclosed_name()` 返回 None → 跳过 | ✅ | 建议记一条 warning（可能有人在试探） |
| C6 | 解压后超 8 GiB | 中止并报错，但**半解压目录留在磁盘**，`extract-progress.json` 仍是 `active:true` | ❌ | 中止时删掉半成品目录；progress 置 `active:false` + `error` |
| C7 | 条目数上万 | 每 200 条写一次进度 | ✅ | — |
| C8 | 同名解压目录已存在 | 追加 `(2)(3)…` 直到 999 | ⚠️ | 同一素材重复导入会堆一堆同名目录；建议复用已有目录或先提示 |
| C9 | 压缩包本身在工程目录内 | `extractOnly` **不检查 overlap**，直接解压到 `Assets/` 旁边，Unity 立刻导入 | ❌ | 解压前做 overlap 检查，命中直接拒绝 |
| C10 | 压缩包在只读目录 / Program Files | 建目录失败 → 「无法创建解压目录」 | ✅ | — |
| C11 | 空 zip | 解出空目录 → 挑选弹窗为空 → 「解压后没有可导入的内容」，空目录不清理 | ⚠️ | 顺手删空目录 |
| C12 | Mac 打包带的 `__MACOSX/` | `walk` 的排除表里没有 → 被当普通目录复制进工程 | ❌ | 加入排除表（`find_zips` 已经排除了，两处不一致） |
| C13 | 解压中用户关窗口 | 后台继续，没有取消入口 | ⚠️ | 至少让任务条能真的中止 |

## 5. D 组 · 解压后挑选（listExtract → importSelected）

| 编号 | 情形 | 现在的处理 | 判定 | 建议 |
|---|---|---|---|---|
| D1 | 解压后顶层只有 1 项 | 不弹窗，直接整目录导入 | ⚠️ | 单目录时仍应先展示「将导入 X，共 N 个文件」 |
| D2 | 解压后顶层 0 项 | 记失败并跳过，目录不清理 | ⚠️ | 顺手清理 |
| D3 | 用户点「跳过」 | 只 `advance()`，解压目录留在磁盘 | ⚠️ | 跳过也应清理临时目录（`keep` 为 false 时） |
| D4 | 勾选 `Assets` | 剥掉这一层，内容直落 `VRCAL_Imports/<名>/` | ✅ | — |
| D5 | 勾选 `Packages` / `ProjectSettings`（VPM 包结构） | 当普通文件夹复制进 `Assets/VRCAL_Imports/<名>/Packages/…` | ❌ | 这种结构应由后端识别并按「完整工程」处理，或明确拒绝并说明 |
| D6 | 勾选一个内含 `.unitypackage` 的子文件夹 | `copy_any` 把包当二进制复制，Unity 里是个无用的 asset | ❌ | 目录里发现包时应递归走包链路，或至少提示 |
| D7 | 目标已有同名文件 | `fs::copy` 静默覆盖 | ❌ | 与 `execute` 的「跳过」统一；覆盖前后都要有记录 |
| D8 | 源 `.meta` 与工程 GUID 冲突 | `importSelected` 不做 GUID 检查 | ❌ | 至少做一次冲突检查，冲突时禁止而非覆盖 |
| D9 | 某个 pick 复制失败 | `copy_any` 用 `?` → 整批抛错，已复制的留在工程里 | ⚠️ | 逐项收集结果，最后汇总 |
| D10 | pick 名里含 `..` | `src_root.join(pick)` 不校验 → 可跳出解压目录 | ❌ | 拒绝含 `..` / 绝对路径的 pick |
| D11 | 所有 pick 都不存在 | 返回 `ok` + 空 jobs，前端记 0 成功、无失败 | ❌ | 应报「勾选的内容都不在了」 |
| D12 | pick 里有包，但助手未装 / Unity 未开 | `execute_sync` 抛错 → `?` 让整批失败，同批文件夹也不导 | ❌ | 包与文件夹分开处理，包失败不牵连复制 |
| D13 | pick 同时有包和文件夹 | 按 pick 顺序执行，文件夹先落盘，包后发 | ⚠️ | 建议文件夹先全部复制完，最后统一发包 |

## 6. E 组 · 文件夹内递归分派（importPath）

| 编号 | 情形 | 现在的处理 | 判定 | 建议 |
|---|---|---|---|---|
| E1 | 文件夹里没有包、只有 zip | 逐个解压 → 递归导入 → 每个子调用自己清理（上限 8 个） | ✅ | 中途某个 zip 失败会中断剩下的，且外层只记「已解压」 |
| E2 | 文件夹里既有包又有文件夹 | `packages` 非空 → **只导包**，文件夹静默丢弃 | ❌ | 两类都处理，或明确提示「本次只导入其中的 N 个包」 |
| E3 | 解压出完整工程结构（Assets + Packages + ProjectSettings） | 只复制 `Assets`，`Packages/` 与 `ProjectSettings/` 静默丢弃 | ❌ | VPM 包必须装进 `Packages/`；至少要警告「依赖包未被安装」 |
| E4 | 解压出 `<名>/Assets/…` | 自动剥一层 Assets | ✅ | — |
| E5 | 解压出 `<名>/<名2>/Assets/…` | 剥单子目录 → 再剥 Assets | ✅（只剥一层） | 三层以上不剥，落点会出现多余层级 |
| E6 | 顶层同时有 `Assets` 和 `说明.txt` | 只导 `Assets`，其余静默丢弃 | ⚠️ | 提示「已忽略 N 个同级文件」 |
| E7 | 顶层 2 个以上目录且无 Assets | 全部塞进 `VRCAL_Imports/<压缩包名>/` | ✅ | 目标名用的是压缩包名而非内容名，可接受 |
| E8 | 与已有导入同名的素材 | 目标名不带 job 后缀 → 与已有目录**合并**，同名文件跳过 | ⚠️ | 与 plan 的 `-<后缀>` 命名不一致，建议统一 |
| E9 | GUID 冲突 / 签名变化导致 execute 抛错 | 抛错向上，解压目录**不清理** | ❌ | 失败路径也要走 cleanup |
| E10 | zip 套 zip | 逐层递归，深度不受限（只有每层 8 GiB 上限） | ⚠️ | 加递归深度上限（如 3 层） |
| E11 | 单个文件复制失败 | 记 warning 继续，最终仍返回成功 | ⚠️ | 同上，区分「完成」与「部分完成」 |
| E12 | 源目录为空 | `execute_sync` 里 `copied=0, skipped=0` → 不命中报错分支 → 写空回执，返回成功 | ❌ | 与 plan 保持一致：空目录直接报错 |

## 13. B5「替换旧版本」的判定规则

替换会动工程里的目录，所以条件收得很紧，三条同时满足才允许：

| 条件 | 说明 |
|---|---|
| 冲突只出现在**一个**导入目录里 | 冲突路径全部形如 `Assets/VRCAL_Imports/<一个目录>/…`；散在多个目录说明不是同一素材，拒绝 |
| 那个目录是**本程序导入的** | 目录里有 `.vrcal-import.json` 回执；没有就是用户自己的目录，拒绝 |
| 目录名以**本素材名**开头 | 旧目录是 `衣装-abcd1234` 或 `衣装`，不会去动 `别的素材-xxxx` |

没有 GUID 冲突时（素材本身不带 `.meta`），额外要求**回执签名与本次内容一致**——同名但不同素材的目录，换掉会毁掉别人场景里的引用。

替换动作：

1. 旧目录 `rename` 到 `<数据目录>/trash/<素材名>-<时间戳>/`（同盘瞬时；跨盘退化成复制 + 删除）
2. 照常复制新内容
3. 一个文件都没复制成功 → 把回收站里的旧目录挪回去，报错（不让用户两头空）
4. 回收站保留 30 天，每次替换时顺手清理过期项；入口路径在 `execute` 返回的 `trashPath` 里

仍然不做的：素材跟工程里**别的资源**撞 GUID 时，永远拒绝（覆盖真的会让引用指错资源）。

## 14. 「导入完成了，队列还在等」——根因与修法（2026-11-05 晚）

### 现象

导入一个 `.unitypackage`（勾选导入，只选了包里的一部分），Unity 里点了 Import 并导完，
「记录」里那条已经显示 **已完成 / 已导入 6 个资源**，但导入队列悬浮窗一直停在：

> 导入 1 / 1：[图标生成(更好用)]IconGenerator
> 已把包发给 Unity：请切到 Unity 窗口，在弹出的导入窗口里点 Import 完成这一步。

队列不推进、不结束，下次启动还会提示「继续上次导入（1 项）」。

### 根因：回调签名不一致（前端 bug，不是 Unity 没回报）

`waitTerminal(ids, done)` 里调用的是 `done(字符串)`：

```js
done(bad.length ? (bad[0].message || 'Unity 导入失败') : '');
```

而两个调用点按数组用：

```js
waitTerminal(waiting, function (rs) {
  if (rs.every(function (x) { return x && x.state === 'completed'; })) { ... }
```

于是 `rs.every is not a function` 抛出 → 该 Promise 变成未处理的 rejection →
`advance()` / `nextItem()` 再也不会被调用 → 队列停在原地。

而「记录」是另一条链路（`checkReceipt` 每 3 秒轮询回执）更新的，所以它是对的。
两条链路一个坏、一个好，就出现了「记录说成功、队列还在转」。

现场证据（用户机器）：
- 回执 `Library/VrclibBridge/Results/e95af76b-….json` → `state: completed`，6 个资源，22:08
- `vrclib-data/workbench.json` 里该 job → `state: completed`
- 同一个文件里 `resume` 还留着这一项 → 说明 `finish()` 没跑过

### 修法

1. **`waitTerminal` 改为 `done(status, message)`**，`status ∈ ok | fail | pending`；
   两处调用点改成按状态记账，不再假设拿到的是数组。
2. **三路结论取其一**，任何一路给出终态就收尾，不再依赖单一通道：
   - 本地记录里同一个 `requestId` 的终态（`checkReceipt` 的结果）
   - Unity 助手写的回执（最权威，带清单核对）
   - 15 分钟看门狗（仍无结论就收尾，队列不允许永远挂着）
3. **`settled` 幂等**：重复的回调、迟到的 Promise 都不会再推进一次队列。

### 顺带修的语义错误

| 状态 | 原来 | 现在 |
|---|---|---|
| `cancelled` | 当成成功（只把 failed 算失败） | 失败：「你在 Unity 导入窗口里取消了导入，工程未改动」 |
| `blocked` | 当成成功 | 失败：带冲突条数与「去记录里点仍要导入」的提示 |
| Unity 没开（请求排队） | 20 秒后当成成功 | `pending`：只是排队，不算成功，写进提示 |

### 「用 Unity 插件监视」这件事

原来就有——导入桥（`Assets/Editor/VrclibImportBridge.cs`）在 Unity 里挂
`importPackageStarted / Completed / Cancelled / Failed` 四个事件，落回执；
`FlushFinal` 还会按包内清单逐条核对 `GUID → 路径`，对不上就降级成 failed。

这次补的是**助手自身的可观测性**：

- 助手每 5 秒写一次 `Library/VrclibBridge/bridge.json` 心跳：
  `{ version, at, active, phase, editor }`
- 桌面端 `receipt` 接口顺带返回 `bridge`（`alive` / `stale` / `missing`）、
  `bridgeVersion`、`bridgeCurrent`、`active`
- 队列据此说话，而不是一律「请切到 Unity 窗口」：
  - `missing` / 版本不符 → 面板上直接给 **「更新 Unity 助手」** 按钮（一键装新版）
  - `stale`（30 秒没心跳）→「Unity 可能正在编译、导包，或者卡住了」
  - `alive` + `active` 为空 →「助手空闲：请求还没被轮询到」
  - `alive` + `active` 非空 →「Unity 正在导入」
- 协议版本 `BridgeVersion = 2`（C#）/ `BRIDGE_PROTOCOL_VERSION = 2`（Rust），
  两边一起改，不一致就提示更新

### 其它

- 「继续上次导入」旁边加了 **「忽略」**：旧版本留下的假记录（其实已经导完）不用再导一遍，点一下就清掉。
- 测试 48 → **51 条**，新增：`heartbeat_reports_version_and_busy_state`、
  `old_heartbeat_is_stale`、`receipt_carries_bridge_state_while_pending`。
