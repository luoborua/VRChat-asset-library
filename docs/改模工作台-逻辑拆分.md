# 改模工作台 · 逻辑拆分

> 目标：把 VRCAL 1.4.1 的「改模与工程」整块能力，按本项目的 Tauri 2 + 原生 JS 架构重新落地。
> 本文是实施前的完整拆解，编号 L01–L42 之后会逐一对应到代码位置。
> 项目按 GPL-3.0 开源；Unity 助手（`assets/unity/*.cs`）原样来自 VRCAL，同为 GPL-3.0，署名见文末。

---

## 0. 三句话总览

1. **工作台不干活，只做三件事**：登记工程、检查准备情况、把文件交进工程并记账。
2. **真正的改模发生在 Unity 里**。程序负责「导入不重复、位置能找到、失败有回执」。
3. **应用与 Unity 之间不靠网络、不靠插件协议，只靠工程目录下的几个 JSON 文件**。

---

## 1. 数据模型

```jsonc
// Project —— 一个已登记的 Unity 工程
{
  "id": "wb_xxx",              // 程序内唯一 id
  "path": "D:\\VRC\\MyAvatar", // 工程根目录（Windows 反斜杠绝对路径）
  "name": "MyAvatar",          // 目录名，仅用于显示
  "unityVersion": "2022.3.22f1",
  "addedAt": "2026-11-04T13:00:00.000Z",
  "lastCheckedAt": "...",
  "missing": false             // 目录不见了标记为 true，不自动删除
}

// Readiness —— 只读检查结果，不落盘
{
  "unityVersion": "2022.3.22f1",
  "checkedAt": "...",
  "dependencies": [
    { "id": "com.vrchat.avatars", "label": "VRChat Avatar SDK",
      "state": "files-found | declared | unknown",
      "version": "3.7.1", "evidence": "Packages/com.vrchat.avatars/package.json" }
  ],
  "notes": ["..."]
}

// ImportJob —— 一次导入的记账
{
  "id": "job_xxx",
  "projectId": "wb_xxx",
  "projectPath": "D:\\VRC\\MyAvatar",
  "sourceName": "SomeOutfit",
  "sourcePath": "E:\\VRChat\\SomeOutfit",
  "mode": "copy | unitypackage",
  "state": "copying | completed | failed | cancelled | waiting-unity",
  "fileCount": 120, "completedFiles": 120,
  "bytes": 52428800, "copiedBytes": 52428800,
  "signature": "sha256:...",     // 内容签名，用于重复导入判定
  "destRel": "Assets/VRCAL_Imports/SomeOutfit-1a2b3c4d",
  "createdAt": "...", "finishedAt": "...",
  "message": "失败原因或提示",
  "repeatOf": "job_xxx"          // 若判定为重复导入，记录上一次的 id
}
```

持久化：`<数据目录>/workbench.json`，结构 `{ schema: 1, projects: [], jobs: [] }`，jobs 只保留最近 100 条。

## 2. 三层职责

| 层 | 文件 | 只做这些 |
|---|---|---|
| Rust 宿主 | `host-sidecar/src/host/workbench_api.rs` | 真正碰磁盘的重活：目录遍历、hash、GUID 索引、复制、启动进程。**不做业务判断** |
| 前端业务 | `renderer/js/91-workbench.js` | 状态机、预检话术、记账、界面渲染；导入由素材库发起（`WB.importToUnity`），本页不再提供选文件入口 |
| Unity 助手 | `assets/unity/VrclibImportBridge.cs` | 接收 `.unitypackage` 请求、调 Unity 原生导入、回执 |

接口统一走已有的 `host_call`：`/api/wb/{op}`，payload 为对象，返回 `{ok:true, ...}` 或抛错。

## 3. 逐条逻辑

### 3.1 工程登记（阶段 1）

| 编号 | 逻辑 | 输入 | 规则 / 输出 | 失败处理 |
|---|---|---|---|---|
| L01 | 选择工程目录 | 用户点「添加工程」 | `FS.host.pickDir()` 拿绝对路径 | 用户取消 → 静默返回 |
| L02 | 工程合法性校验 | 路径 | 必须同时存在 `Assets`、`Packages`、`ProjectSettings` 三个**目录**（不是文件） | 缺哪项就说缺哪项，不登记 |
| L03 | 路径归一 | 路径 | 去尾部分隔符、转反斜杠、转小写比较（仅比较用，存原样） | — |
| L04 | 读 Unity 版本 | 路径 | 读 `ProjectSettings/ProjectVersion.txt` 第一行 `m_EditorVersion: 2022.3.22f1` | 读不到 → `unityVersion: ""`，不阻断登记 |
| L05 | 去重登记 | 归一后的路径 | 已存在 → 复用原记录（保留 `addedAt`），并选中它 | — |
| L06 | 拒绝危险路径 | 路径 | 工程根不得是盘符根、不得包含数据目录、不得包含素材库目录 | 明确报错，拒绝登记 |
| L07 | 记住最近选择 | projectId | 写入 `workbench.json.lastProjectId` | 记录指向的工程没了 → 退回空选，不自动挑 |
| L08 | 删除登记 | projectId | 仅移除记录与历史，**不动磁盘** | 二次确认 |

### 3.2 工程准备情况（阶段 1）

| 编号 | 逻辑 | 规则 |
|---|---|---|
| L09 | 只查三个公开依赖 | `com.vrchat.avatars`、`nadena.dev.modular-avatar`、`nadena.dev.ndmf`。不枚举 Assets，不执行包代码 |
| L10 | 版本来源优先级 | ① `Packages/<id>/package.json` ② `Packages/vpm-manifest.json` ③ `Packages/packages-lock.json` ④ `Library/PackageCache/<id>@<ver>/package.json` |
| L11 | 状态判定 | 读到真实 `package.json` 且 `name` 匹配 → `files-found`；只有声明 → `declared`；都没有 → `unknown` |
| L12 | 固定提示 | 页面常驻一句：「包文件存在不代表编译通过，最终以 Unity 结果为准」 |
| L13 | 备注生成 | 某文件读失败 → 记一条 note，**不把它当成有效证据**，也不当成失败 |

### 3.3 素材来源枚举（阶段 2）

| 编号 | 逻辑 | 规则 |
|---|---|---|
| L14 | 目录 → 文件清单 | 递归，深度 ≤ 6，条目 ≤ 20000，超出即报错（不静默截断） |
| L15 | 排除目录 | `.git`、`Library`、`Temp`、`node_modules`、`obj`，且**跳过符号链接**（防目录环） |
| L16 | 排除文件 | 可执行与脚本：`.exe .msi .bat .cmd .ps1 .lnk .url`，不复制进工程 |
| L17 | `.unitypackage` 识别 | 扩展名命中 + 读头两字节 `1f 8b`（gzip）；不是就报「不是有效的 Unity 素材包」，不硬导入 |
| L18 | 清单与签名 | 每个文件取 `相对路径 + 字节数`，排序后 sha256 得 `signature`。签名只用于「是不是同一份东西」 |
| L19 | 路径重叠拒绝 | 素材不得在工程内，工程不得在素材内（互相包含都拒绝） |

### 3.4 导入预检（阶段 2）

| 编号 | 逻辑 | 规则 |
|---|---|---|
| L20 | 目标目录 | `Assets/VRCAL_Imports/<素材名净化>-<8位十六进制>`。净化：去掉 `\/:*?"<>|`，压缩空白，限长 60 |
| L21 | GUID 冲突检查 | 遍历工程 `Assets/**/*.meta`，取 `guid:` 行；与本次要复制进来的 `.meta` 的 GUID 求交集。命中 → **禁止导入**（不提供「强行覆盖」按钮） |
| L22 | 重复导入检测 | 同工程 + `mode` + `signature` 相同 → 判定重复，展示上次记录；`.unitypackage` 允许手动「仍要导入」 |
| L23 | 预检结论 | 三项：目标工程路径、文件引用（GUID）、角色适配（固定 `unknown`，因为程序不知道） |
| L24 | 预检不落盘 | 预检只是展示。用户点「导入」才写文件 |

### 3.5 复制执行（阶段 2）

| 编号 | 逻辑 | 规则 |
|---|---|---|
| L25 | 执行前复验 | 重新枚举 + 重算签名，与预检时不一致 → 中止，要求重来 |
| L26 | 逐文件复制 | 保留相对目录结构；`.meta` 一并复制；已存在同名文件 → **跳过并计入 warnings**，绝不覆盖 |
| L27 | 进度 | 每 50 个文件或每 200ms 更新一次 `completedFiles / copiedBytes` |
| L28 | 回执 | 写 `<目标目录>/.vrcal-import.json`：`{schema:1, id, signature, dest, files, bytes, state:"completed", at}` |
| L29 | 中断恢复 | 启动时若存在 `state:"copying"` 的 job：检查回执，完整则转 `completed`，否则转 `failed` 并提示可重试 |
| L30 | 不改动原素材 | 复制模式全程只读源目录 |

### 3.6 记账（阶段 2）

| 编号 | 逻辑 | 规则 |
|---|---|---|
| L31 | 持久化 | 每次状态变化写 `workbench.json`；先写 `.tmp` 再 rename，避免半截文件 |
| L32 | 保留上限 | 100 条，超出丢最旧；被丢弃的 job 不影响磁盘上的回执 |
| L33 | 状态机 | `copying → completed / failed`；`waiting-unity → completed / failed / cancelled`。终态不再变 |
| L34 | 记录人工检查 | 「外观/动作/菜单」三项勾选，只记在 job 上，不据此自动判定成功 |

### 3.7 `.unitypackage` 交接（阶段 3，未实现）

## 7. 阶段 3 实施记录（.unitypackage 直接导入）

按用户要求，Unity 侧助手**没有复用** VRCAL 的 `VRCALImportBridge.cs`，而是按同一协议思路
**全新重写**为 `assets/unity/VrclibImportBridge.cs`（自己的命名空间 `VrcLib.Workbench`、
自己的目录布局与回执字段），文件由 Rust 侧 `include_str!` 编译期嵌入，运行时通过
`/api/wb/installBridge` 写入目标工程的 `Assets/Editor/`。

### 文件桥协议

```
Library/VrclibBridge/Requests/<uuid-v4>.json          本程序写入的导入请求
Library/VrclibBridge/Requests/<uuid-v4>.json.claimed  Unity 助手已认领（重命名即互斥锁）
Library/VrclibBridge/Results/<uuid-v4>.json           Unity 助手写回的回执
```

- 请求：`{ schema:1, id, project, package, sha256 }`；`project` 必须与当前工程根一致（防串工程），
  `sha256` 为包文件哈希（认领时复算，预览后包被换掉即失败）。
- 回执：`{ schema:1, id, sha256, state, message, assets, assetsComplete }`，
  `state`：`importing → completed / cancelled / failed`。
- 幂等：认领改名互斥 + 已有最终回执的请求直接跳过；Unity 中途被关掉，下次启动把孤儿请求标记为 failed。

### 新增 API

| API | 说明 |
|---|---|
| `plan`（包模式） | 返回 sha256 签名、大小、`bridgeInstalled`（工程里有没有助手）、`ready` |
| `execute`（包模式） | 复验 sha256 → 生成 UUID v4 → 原子写请求文件，返回 `requestId` |
| `receipt` | 查询回执；没有回执时返回 `queued`（Unity 没开）或认领中 |
| `installBridge` | 把内嵌的助手源码写进 `Assets/Editor/VrclibImportBridge.cs`，已装则幂等返回 |

前端：导入入口改为「文件夹 / Unity 素材包」双选；包模式记录进入 `waiting-unity` 状态，
工作台打开期间每 3 秒轮询回执，完成后展示 Unity 上报的资源路径并可打开所在目录。

## 8. 阶段 4 实施记录（MA 自动装配）

> **2026-11-06：整个 MA 装配模块已移除。** 删除的东西：`assets/unity/VrclibMASetup.cs`、
> Rust 侧的 `maRequest` / `maReceipt` 两个接口与 `MARequests` / `MAResults` 文件桥、
> `installBridge` 里的第二个文件、`probe` 的 `maInstalled`、复制导入返回的 `prefabs` 字段、
> 前端两种导入预览页的「导入后用 MA 装配」复选框与任务行的装配状态。
>
> 原因：装配效果对素材结构太敏感（骨骼命名、MergeArmature 绑定、作者自带菜单各不相同），
> 自动化出来的结果经常还不如在 Unity 里手动拖一次，维护成本却很高。
> **工程里已经装过 `VrclibMASetup.cs` 的，升级程序后那个文件不会再被更新，可以自己删掉**，
> 删掉不影响导入助手。下面几段是移除前的设计记录，只作历史参考。

同样**不复用** VRCAL 的 `VRCALMASetup.cs`，全新重写为 `assets/unity/VrclibMASetup.cs`
（命名空间 `VrcLib.Workbench`，与导入桥同住 `Library/VrclibBridge/` 协议根）。

### 文件桥协议

```
Library/VrclibBridge/MARequests/<uuid>.json   本程序写入的装配请求
Library/VrclibBridge/MAResults/<uuid>.json    Unity 侧 MA 助手写回的回执
Library/VrclibBridge/MAState/<uuid>.json      进行中日志（中断后禁止自动重放的依据）
```

- 请求：`{ schema:1, id, sha256, project, sourceName, mode, importId, prefabPaths, assemble, menu }`
  - 复制模式：`prefabPaths` 由桌面程序从复制结果里筛出的 `.prefab` 相对路径；
  - 包模式：`importId` 指向导入桥的请求，装配必须等那次导入回执 `completed`。
- 回执：`state: waiting-import → waiting-selection → applied / skipped / error`。

### 装配流程（Unity 侧）

1. 轮询 MARequests，依赖检查（VRCAvatarDescriptor + MA 组件类型 + SetupOutfit 方法，全反射）。
2. 场景角色枚举（跳过预制件编辑模式）；**唯一角色 + 唯一已知预制件时自动装配**，
   否则弹中文选择窗口（`Tools/素材库/MA 装配导入的预制件`）。
3. 装配本体：Undo 组 + RegisterFullObjectHierarchyUndo(角色) → InstantiatePrefab 挂角色下 →
   校验 MergeArmature/BoneProxy 绑定指向角色 → 无绑定且是骨骼服装（蒙皮/人形/Hips）时
   反射调 `SetupOutfit.SetupOutfitUI` → 复验绑定 → 置为最后一个子物体。
4. 可选菜单：作者已带 MA 菜单组件则保留；否则建 MenuInstaller + MenuItem(Toggle) +
   ObjectToggle（参数 `VrcLibMenu_<id>`，开关控制实例显隐）。
5. 失败 `Undo.RevertAllDownToGroup` 整体回滚；Unity 中途被关 → 下次启动只标 error 不重放。

### 新增 API

| API | 说明 |
|---|---|
| ~~`maRequest`~~ | 已移除 |
| ~~`maReceipt`~~ | 已移除 |
| ~~`execute` 的 `prefabs`~~ | 已移除 |
| `installBridge` | 只装导入桥，已存在的跳过 |

前端：两种导入的预览页都有「导入后用 MA 装配」复选框（默认关）和「同时接入显隐菜单」子选项；
记录行展示 MA 状态（等待/已完成→层级路径/跳过/失败），轮询与导入回执共用一个 3 秒定时器。
## 9. 阶段 3/4 硬化记录（冲突闸门与死锁修复）

这一节只记 2026-11 的硬化改动，不替代第 7、8 节的协议描述。

### 9.1 请求 / 回执字段（冻结）

请求 `Library/VrclibBridge/Requests/<uuid>.json`：

```
{ "schema":1, "id", "project", "package", "sha256",
  "bytes": <int64>, "allowOverwrite": <bool> }
```

回执 `Library/VrclibBridge/Results/<uuid>.json`：

```
{ "schema":1, "id", "sha256", "state", "message",
  "assets": [], "assetsComplete": <bool>,
  "conflicts": [ { "guid", "existingPath", "packagePath" } ],
  "overwrote": [], "manifestComplete": <bool>,
  "package", "packageBytes" }
```

- `state`：`importing | completed | cancelled | failed | blocked`。
- `bytes` 是包文件长度（桌面端写请求时从文件 metadata 取，Unity 侧可据此预检）。
- `allowOverwrite` 默认 `false`；只有「仍要导入」才置 `true`。
- `conflicts` 只在 `blocked` 时有内容；`overwrote` 记录本次真正覆盖掉的已有资源；
  `manifestComplete=false` 表示 Unity 侧的工程清单没扫全（列表可能不完整）。
- `package` / `packageBytes` 是 Unity 回写时对「它实际读的那个包」的确认，
  桌面端用它做覆盖前的一致性校验。

### 9.2 `blocked` 的语义

Unity 助手发现 GUID 冲突（包内某个 `.meta` 的 GUID 在工程里已存在）时：

1. **不导入任何资源**，不覆盖同名文件；
2. 写一条 `state:"blocked"` 的回执，带上 `conflicts`、`package`、`packageBytes`、`sha256`；
3. **删掉自己的 `.claimed`**，也就是明确表示「我不会自动重试」。

所以 `blocked` 不是失败，也不是「等 Unity 再想想」。它是一个死锁点：
桌面端不重新下发请求，这个 job 会永远停在 waiting-unity。
前端因此把 `blocked` 映射成 `attention`（需要处理），并保留 `waiting-unity` 状态继续轮询。

### 9.3 「仍要导入」怎么走

新增 API `/api/wb/allowOverwrite`（入参 `projectRoot` + `requestId`）：

1. 校验 requestId 必须是 UUID 形状，`require_project` 校验工程；
2. 读 `Results/<id>.json`，**必须存在且 `state == "blocked"`**，否则报
   「这条导入没有待确认的冲突」；
3. 从回执取 `package` / `sha256` / `packageBytes`，校验包文件仍存在、
   长度与 `packageBytes` 一致、流式 `sha256` 与回执一致；任一不符就报错，
   要求重新预检（预检后包被换掉时不能盲目覆盖）；
4. 把旧回执 rename 成 `Results/<id>.json.superseded-<毫秒时间戳>`（保留证据，
   同时让轮询立刻看不到这条 blocked）；
5. 原子写同 id 的新请求：先写 `.tmp` 再 rename，字段与原请求一致，
   但 `allowOverwrite:true`、`bytes` 为实际文件长度；
6. 返回 `{ ok:true, requestId, state:"waiting-unity" }`。

前端在记录行给「仍要导入（覆盖同名资源）」和「放弃这次导入」两个按钮。
前者成功后清掉 `job.blocked` / `job.conflicts`、把 message 改成「已允许覆盖，等待 Unity 重新处理」并继续轮询；
后者把 job 置为 `cancelled`，Unity 侧本来就不会再执行（`.claimed` 已删），
所以这个操作只把桌面端的记录收口，不需要再写文件。

### 9.4 Unity 侧重载之后

- 重新编译 / 重载域后，助手按启动顺序扫描 `Requests/`：
  没有 `.claimed` 的请求才会被执行；`blocked` 留下的旧请求不会复活。
- 新下发的 `allowOverwrite:true` 请求被认领后，Unity 用包内 GUID 覆盖工程里
  已存在的同名资源，然后写 `completed`，并在 `overwrote` 里列出被覆盖的现有路径。
- 桌面端收到 `completed` 后清 `blocked`，记录 `importedAssets` / `assetsComplete` /
  `overwrote` / `manifestComplete` / `packagePath` / `packageBytes`；
  `overwrote` 非空时在记录里显示「覆盖了 N 个已有资源」。
- `superseded-*` 文件不会被任何一方读取，只是归档；清理磁盘时可连同旧 `Results` 一起删。

### 9.5 另外几处硬化

- **gzip 魔数**：`plan` 与 `execute` 的包分支都先读头两字节，不是 `1f 8b` 就拒绝，
  错误文案固定为「这不是有效的 Unity 素材包（不是 gzip 格式）」。
  误改后缀的普通文件在预检阶段就被挡住，不再交给 Unity。
- **4 GiB 上限**：`execute_package` 在算 sha256 之前检查文件长度，超过 4 GiB 直接拒绝，
  避免把超大文件整个读穿。
- 前端修了状态归类的两个老问题：`blocked` 不再被当成 `failed`；
  `cancelled` 归入「已完成」而不是「等待处理」。
